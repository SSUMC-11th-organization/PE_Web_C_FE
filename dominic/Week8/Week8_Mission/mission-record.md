# 8주차 미션 기록

## 수행 범위

회원가입을 useMutation으로 리팩터링하고, 로그인·내 정보·즐겨찾기·평점 API를 연결했다. 필수 미션인 로그인 전용 Route Group/Layout Route, 선택 미션인 캐시 갱신 비교와 mutationOptions 리팩터링을 함께 수행했다.

7주차 앱을 Week8_Mission으로 복사해 독립 실행했다. 초기에는 기존 7주차 서버에 즐겨찾기 API가 없어 모의 응답을 준비했고, 새 8주차 백엔드가 만들어진 뒤 실제 계약과 연결해 전체 HTTP 시나리오까지 확인했다. 백엔드 코드는 이 작업에서 수정하지 않았다.

## 1. 회원가입과 로그인

- 회원가입의 별도 isSubmitting 상태와 try/catch 요청을 useSignupMutation으로 옮겼다. 진행 여부는 isPending, 성공·실패는 mutation 콜백으로 처리한다. 형식 검사, 두 중복 확인, 값 변경 시 확인 초기화, 실패 시 입력 유지는 유지했다.
- 로그인은 공개 apiClient로 POST /auth/login을 호출한다. 성공한 accessToken만 Zustand persist에 보관하고, 내 정보 Query를 무효화한 뒤 홈으로 이동한다.
- 잘못된 비밀번호는 입력을 지우지 않고 실패를 안내해 다시 제출할 수 있게 했다. 요청 중 입력과 버튼을 비활성화하고, 연속 제출은 ref 잠금으로 막는다.
- 로그인 상태로 /login을 직접 열면 홈으로 이동한다. 토큰을 갖고 있다는 사실만으로 인증을 확정하지 않고, GET /members/me 응답으로 유효성을 확인한다.

## 2. 로그인 전용 폴더와 공통 레이아웃

```text
src/routes/
├─ __root.tsx
├─ login.tsx
├─ signup.tsx
└─ (authenticated)/
   ├─ _authenticated.tsx
   └─ _authenticated/
      ├─ my.index.tsx
      └─ my.edit.tsx
```

Route Group은 파일을 묶고 pathless Layout Route는 공통 인증 확인과 Outlet 렌더링을 담당한다. 그룹과 레이아웃 이름은 URL에 포함되지 않아 /my, /my/edit 주소를 유지한다. beforeLoad에서 비로그인 접근을 차단하고, 공통 레이아웃은 조회 진행·오류·재시도를 처리한다.

## 3. 서버 상태와 토큰 분리

회원 정보의 원본은 서버에 있으므로 전역 store에 별도 복사하지 않았다. 헤더·조회·수정 화면이 같은 회원 Query를 사용해 닉네임 변경을 함께 반영한다. 토큰은 요청에 사용할 클라이언트 상태로 관리한다.

개인 Query key에는 토큰 문자열 대신 세션 번호를 넣었다. 로그인·로그아웃 때 세션 번호를 바꾸어 이전 회원의 데이터가 새 화면에 섞이지 않게 했다. 세션이 바뀌면 개인 Query를 중단·제거하고 라우터의 접근 조건을 다시 검사한다.

인증 ky 인스턴스는 요청 직전에 최신 토큰을 읽어 헤더에 넣는다. 401 응답은 토큰을 제거하되, 늦게 도착한 예전 요청의 401이 새 로그인 토큰을 지우지 않도록 요청 토큰과 현재 토큰을 비교한다. 인증 조회와 mutation은 자동 재시도하지 않는다.

## 4. 남은 API 연결

| API | 화면 연결과 갱신 |
| --- | --- |
| GET/PATCH /members/me | 헤더·마이페이지·닉네임 수정 |
| GET /favorites | 마이페이지와 카드·헤더의 동일한 서버 목록 |
| GET /favorites/:movieId | 영화 상세의 즐겨찾기 여부 |
| POST /favorites | 등록 성공 후 상세 상태 캐시 갱신·목록 무효화 |
| DELETE /favorites/:movieId | 해제 후 목록과 카운트 재조회 |
| GET /members/:memberId/ratings | 현재 회원 평점에서 해당 영화의 기록 선택 |
| POST /ratings | 최초 평점 등록 후 목록 재조회 |
| PATCH /ratings/:ratingId | 점수·후기 수정 후 목록 재조회 |
| DELETE /ratings/:ratingId | 삭제 후 빈 등록 폼으로 전환 |

즐겨찾기와 평점은 이전 localStorage 사본을 사용하지 않는다. 즐겨찾기 목록의 movieId로 TMDB 상세를 조회하고 한 번에 5편씩 보여준다. 조회 실패를 빈 목록이나 미등록 상태로 숨기지 않고 오류와 재시도를 제공한다.

평점은 1~5점과 선택 후기 500자 제한을 적용했다. 서버가 토큰으로 소유자를 결정하므로 쓰기 본문에 memberId를 넣지 않는다. 성공 후 재조회까지 mutation 진행 상태를 유지하고, 실패하면 사용자가 입력한 점수·후기를 보존한다.

## 5. 선택 미션: 캐시 갱신 두 방식

닉네임 수정 응답은 회원 조회와 같은 형태이므로 기본 모드에서는 setQueryData로 갱신했다. 비교 모드에서는 invalidateQueries로 활성 회원 Query를 다시 조회한다. 진행 중이던 이전 GET이 PATCH 응답을 덮어쓰지 않도록 먼저 해당 Query를 취소한다.

```ts
await client.cancelQueries({ queryKey: accountKeys.me(session) });
if (mode === 'direct') {
  client.setQueryData(accountKeys.me(session), member);
} else {
  await client.invalidateQueries({ queryKey: accountKeys.me(session) });
}
```

| 동일한 조건의 통합 테스트 | 수정 요청 | 수정 후 추가 회원 GET | 화면 반영 |
| --- | --- | --- | --- |
| direct | PATCH 1회 | 0회 | PATCH의 최신 회원 응답을 즉시 사용 |
| invalidate | PATCH 1회 | 1회 | GET이 반환한 서버 원본을 사용 |

이 횟수는 모의 요청 함수를 사용한 Query/화면 통합 테스트로 확인했다. 실제 브라우저에서도 두 모드의 닉네임 변경을 확인했지만, Network 패널에서 요청 수를 직접 센 기록은 아니다.

서버 응답에 최신 조회 데이터가 있으면 직접 갱신이 적절하다. 평점 생성·삭제처럼 목록·정렬을 다시 맞춰야 하거나 응답에 최신 목록이 없으면 재조회를 선택했다. 직접 갱신은 서버 성공 후 수행하므로 낙관적 업데이트와는 다르다.

## 6. 선택 미션: mutationOptions

queries/account.ts에 회원가입·로그인·내 정보 수정·즐겨찾기·평점 mutationOptions를 모았다. 요청 함수, 재시도 설정, 관련 캐시 갱신 규칙을 재사용하고 페이지에는 입력값과 제출·이동 동작을 남겼다. 회원가입과 로그인은 별도 커스텀 훅으로 연결했다.

## 트러블슈팅

**서버 준비 전 즐겨찾기 404**: 기존 7주차 서버에는 /favorites가 없어 오류가 났다. 이를 빈 목록으로 바꾸지 않고 실제 연결 실패로 표시했다. 새 8주차 코드와 실제 응답을 확인한 뒤 3008 검증 서버로 연결했고 등록·목록·상태·해제를 모두 확인했다.

**예전 세션의 응답과 캐시**: 회원 캐시 key를 전역 고정 값 하나로만 두면 계정 변경 중 이전 응답이 표시될 수 있다. 세션 번호를 포함하고, 세션 변경 시 개인 Query를 취소·제거했다. mutation 성공 콜백도 시작한 세션이 아직 현재 세션인지 확인한다.

**평점 재조회 후 성공 안내 소실**: 서버 결과로 폼을 새로 구성할 때 폼 내부의 성공 메시지도 초기화될 수 있다. 결과 안내를 상위 평점 패널에 두어 폼이 바뀐 뒤에도 보이도록 했다.

**라우트 파일 Fast Refresh 검사**: Route와 화면 컴포넌트가 한 파일에 함께 있을 때 ESLint 규칙에 걸렸다. 인증 레이아웃 화면을 components/auth로 옮겨 라우트 연결과 화면 책임을 분리했다.

HTTP 검증 결과는 docs/api-verification.json에 상태 코드와 경로만 남겼다. 실제 토큰·비밀번호·Authorization·로그인 원본 응답은 저장하지 않았다. 캡처는 docs/screenshots에 첨부했다.

브라우저 검증 회원과 HTTP 검증 회원은 서로 다른 테스트 계정이다. HTTP 스크립트가 만든 평점·즐겨찾기는 검증 후 삭제했고, 화면 확인용 회원의 영화 1편과 평점은 확인 화면용으로 남겼다. 기존 계정과 테이블은 삭제하지 않았다.

## 배운 점

서버의 데이터 변경과 브라우저 캐시 변경은 별개의 일이다. mutation이 성공한 뒤 어떤 Query를 어떻게 갱신할지 정해야 화면이 일치한다. 같은 회원 정보를 여러 저장소에 중복 보관하지 않고, 계정 전환과 실패 상황까지 고려해야 정상 흐름뿐 아니라 경계 상황에서도 올바른 데이터를 보여줄 수 있다.

Notion 원본과 과제 제출 시스템에는 직접 입력하지 않았다. [핵심 키워드](../core-keywords.md)와 이 기록을 옮겨 작성할 수 있다.
