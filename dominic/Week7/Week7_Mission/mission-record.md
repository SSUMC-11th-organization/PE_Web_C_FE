# 7주차 미션 기록

## 수행 범위

워크북 본문의 회원가입 API 실습, 필수 미션인 로그인·내 정보 조회·수정 화면, 선택 미션인 내 정보 페이지 폴더 구조 설계를 진행했다. 6주차 영화 앱을 `Week7_Mission`에 복사해 기존 영화 기능을 유지하고, `pages/auth`와 `pages/my`를 추가했다.

## 회원가입 실습

1. `/signup`에 이메일·닉네임·비밀번호·비밀번호 확인을 연결했다. 입력값은 `useState`로 관리하고 입력을 시작한 필드에 형식 오류를 표시했다. 이메일 형식, 닉네임 2~12자, 영문 대·소문자·숫자·특수문자를 모두 포함하는 8자 이상 비밀번호와 재입력 일치를 검사한다.
2. 형식이 올바르면 이메일·닉네임 중복 확인 API를 호출한다. 확인 중에는 해당 입력과 버튼을 잠그고, 사용할 수 있는 값인지 입력 아래 안내한다. 확인한 값을 수정하면 해당 결과를 초기화한다.
3. 모든 입력 검증과 두 중복 확인을 통과해야 가입 버튼이 활성화된다. 가입 요청에는 `passwordConfirm`을 제외한 세 필드만 보낸다. 제출 중에는 입력과 버튼을 잠그고 `가입 중`으로 문구를 바꾼다. 연속 클릭·Enter 반복에 대비해 ref 잠금도 함께 사용했다.
4. 성공하면 서버 메시지를 표시하고 비밀번호 두 필드를 비운다. 실패하면 입력값을 유지하고 오류를 안내한다. 확인 이후 다른 사용자가 먼저 가입했을 가능성도 있어, 재시도 전 두 중복 확인을 다시 받도록 했다. 자동 재시도는 꺼서 회원 생성 요청을 임의로 반복하지 않는다.

핵심 조건은 `canSubmit`에 모았다.

```ts
const canSubmit =
  emailValid && nicknameValid && passwordValid && confirmValid &&
  checks.email.checkedValue === form.email.trim() &&
  checks.nickname.checkedValue === form.nickname.trim() &&
  !checks.email.checking && !checks.nickname.checking &&
  !isSubmitting && !feedback.success;
```

## 필수 미션

- **로그인**: 이메일·비밀번호 입력과 버튼 활성화, 회원가입 이동을 구현했다. 실제 로그인 API는 다음 주차 범위라 제출 시 준비 중임을 안내하며 로그인에 성공한 것처럼 처리하지 않는다.
- **내 정보 조회**: Figma의 넓은 레이아웃을 참고해 기본 정보와 즐겨찾기 목록을 배치했다. 기본 정보는 예시 데이터를 사용하고, 즐겨찾기는 기존 Zustand의 영화 ID를 사용해 상세 Query 캐시와 연결한다. 한 번에 5개씩 조회하며 로딩·실패·재시도·빈 목록도 구분한다.
- **내 정보 수정**: 닉네임·이메일 입력, 프로필 이미지 선택과 미리보기, 수정·취소를 구현했다. 이미지는 PNG/JPG/WebP, 5MB 이하를 검사한다. 수정하기는 예시 상태에 반영한 뒤 조회 화면으로 이동하고, 취소는 변경을 버린다. 비밀번호 변경·탈퇴 버튼은 디자인에 맞춰 표시하되 준비 중 안내만 제공한다.
- 화면별 제목과 입력 label, 오류 설명 연결, 요청 결과의 `status`/`alert`, 작은 화면에서 세로로 바뀌는 배치를 적용했다. 기존 폴더의 아이콘과 포스터를 복사해 사용했다.

## 선택 미션: 폴더 구조

```text
src/
├─ routes/
│  ├─ signup.tsx
│  ├─ login.tsx
│  ├─ my.index.tsx
│  └─ my.edit.tsx
├─ pages/
│  ├─ auth/           # 회원가입·로그인
│  └─ my/             # 내 정보 조회·수정
├─ components/
│  ├─ auth/           # 공통 입력 필드·폼 스타일
│  └─ my/             # 프로필 이미지·북마크 목록
├─ api/members/       # 중복 확인·회원가입 요청 및 응답 검증
├─ stores/            # 예시 프로필 상태, 기존 북마크 등
└─ utils/auth/        # 입력 유효성 검사
```

라우트 파일은 URL과 페이지를 연결하고, 실제 화면은 `pages/my`에 묶었다. 다음 주 인증이 추가될 위치를 쉽게 찾도록 구분했으며 이번에는 전용 layout이나 접근 제한을 구현하지 않았다. 프로필은 메모리 상태여서 새로고침하면 초기값으로 돌아가고 실제 계정은 변경되지 않는다.

## 트러블슈팅

### 1. API 응답 형식 차이

워크북은 중복 확인 결과를 `{ available }`로 설명하지만 기존 NestJS 6주차 서버는 `{ isSuccess, result: { available } }`로 반환했다. `response.available`만 읽으면 사용 가능한 값도 실패로 처리된다. 요청 함수에서 `result`를 풀고 boolean인지 검사하도록 수정했다. HTTP 200이어도 `isSuccess: false`면 오류로 처리한다.

### 2. 확인한 값과 실제 제출 값의 불일치

중복 확인 성공을 boolean만으로 보관하면, 값을 수정해도 이전 결과로 가입할 위험이 있다. 성공한 실제 값을 `checkedValue`에 보관하고 현재 입력과 비교한다. 입력 변경 시 결과를 초기화하고 요청 중 해당 필드는 비활성화해 확인 도중의 변경도 막았다.

### 3. 회원 서버 연결과 인증 헤더 분리

워크북 기본 주소는 8080이지만 로컬 회원 서버는 3004를 사용한다. 환경 변수로 주소를 분리하고 서버 CORS에 5179 프론트 주소를 허용해 연결했다. TMDB 클라이언트와 별도 ky 인스턴스를 사용해 영화 조회 토큰이 회원 서버에 전송되지 않도록 했다. `.env.local`과 실제 토큰은 Git에서 제외한다.

## 배운 점

입력 형식 검사와 서버 중복 확인은 역할이 다르다. 중복 확인에 통과해도 최종 저장 시 충돌할 수 있어 가입 실패 처리가 필요하다. 화면에서 상태를 표시하는 것과 실제 인증·인가도 다르므로, 예시 프로필과 실제 회원가입 결과를 혼동하지 않도록 구분하는 것이 중요했다.
